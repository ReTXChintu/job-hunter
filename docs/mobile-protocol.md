# Mobile relay protocol

This is the source of truth for the JSON spoken between the desktop app, the
relay, and the Flutter mobile app. Rust (`crates/job-hunter-core/src/remote`,
`crates/job-hunter-relay`) and Dart (`apps/mobile/lib/models`,
`apps/mobile/lib/services`) each hand-implement it, the same way
`packages/types` hand-mirrors the Rust domain model. Change this file and
both implementations together.

## Why a relay exists

The mobile app never talks to Claude, Chrome, MongoDB, or the desktop's local
file store directly. It only ever does two things:

1. REST calls to the relay for **account and device identity** (register,
   log in, register a device, create/redeem a pairing code, list/revoke
   devices).
2. One **WebSocket** to the relay for **presence and live requests**: "is my
   desktop online right now", and "ask my desktop to do X and give me the
   answer". The relay forwards bytes between the one desktop connection and
   any mobile connections for the same account; it never reads job or resume
   content, and it never runs any AI.

All actual work — reading jobs/applications, approving, applying, answering
questions — happens on the desktop, through the exact same `AppContext` /
`orchestrator` functions the Tauri UI calls. The relay and the phone cannot
do anything the desktop UI couldn't already do, and every approval still
goes through `Application::can_transition_to`.

If the desktop is offline, the relay has nothing to forward: the phone shows
its last cached snapshot with a "Desktop offline" banner and disables
actions that need a live desktop.

## Accounts and devices

- One relay account (email + Argon2id-hashed password) can have any number
  of **devices**: exactly one is meant to run as `kind: "desktop"` at a
  time (the Job Hunter installation), any number as `kind: "mobile"`.
- A device is identified by an opaque, high-entropy **device token** (not a
  JWT — a random 32-byte value, stored server-side only as its SHA-256
  hash). It never expires on its own; it is revoked explicitly from the
  desktop's Settings → Remote & Mobile → Paired devices list, or by
  logging out.
- **Pairing codes** are the normal way to add a phone: the already
  logged-in desktop calls `POST /v1/pairing/create`, which returns a
  6-character code good for 5 minutes. The phone calls
  `POST /v1/pairing/redeem` with that code and gets back a device token —
  no email or password typed on the phone. The desktop shows the code as
  both text and a QR (the QR payload is `{"relayUrl","code"}` as JSON so
  the phone's scanner can pre-fill the server address too).
- Email + password login on the phone is the fallback (reinstall, second
  phone without access to the desktop at that moment).

## REST endpoints

Base path `/v1`. All bodies and responses are JSON. Errors are
`{"error": {"code": "...", "message": "..."}}` with a 4xx/5xx status.

| Method & path | Auth | Body | Returns |
| --- | --- | --- | --- |
| `POST /auth/register` | none | `{email, password, displayName?}` | `{userId, accessToken, refreshToken}` |
| `POST /auth/login` | none | `{email, password}` | `{userId, accessToken, refreshToken}` |
| `POST /auth/refresh` | none | `{refreshToken}` | `{accessToken, refreshToken}` (rotated) |
| `POST /auth/logout` | none | `{refreshToken}` | `{}` (revokes that refresh token) |
| `POST /devices/register` | Bearer accessToken | `{name, kind: "desktop"\|"mobile", platform}` | `{deviceId, deviceToken}` |
| `GET /devices` | Bearer accessToken | — | `{devices: [{id, name, kind, platform, online, lastSeenAt, createdAt}]}` |
| `DELETE /devices/:id` | Bearer accessToken | — | `{}` (closes any live socket for that device) |
| `POST /pairing/create` | Bearer accessToken (desktop's) | `{}` | `{code, expiresAt}` |
| `POST /pairing/redeem` | none | `{code, name, platform}` | `{deviceId, deviceToken, userId}` |
| `GET /ws` | `?token=<deviceToken>` query param (WebSocket upgrade) | — | — |

`accessToken` is a short-lived JWT (15 minutes) used only for the REST
calls above; `refreshToken` is a long-lived opaque token (30 days, rotated
on use, stored hashed) used to mint new access tokens without asking for
the password again. `deviceToken` is separate again and is what
authenticates the WebSocket — it is what both apps persist for day-to-day
use (desktop and mobile do not keep the password or refresh token around
after initial login/registration; the device token is enough for
everything the phone needs afterwards).

## WebSocket envelope

Every frame, both directions, is one JSON object:

```json
{ "v": 1, "id": "<uuid, request/response correlation>", "type": "<message type>", "payload": { ... } }
```

- `id` is generated by whoever initiates a request and echoed back on the
  matching `response`. Push messages the relay or desktop originate on
  their own (`presence`, `changed`, `agent_status`) use a fresh `id` that
  nothing needs to correlate against.
- The relay only inspects `type`; it never reads inside `payload`. It
  routes every frame from a mobile device straight to the one connected
  desktop device for that account, and vice versa. If no desktop is
  connected, the relay immediately replies to the mobile device with a
  synthetic `{"type":"response","id":<same id>,"payload":{"ok":false,"error":{"code":"DESKTOP_OFFLINE","message":"..."}}}` — it never queues requests.

### Relay-originated

- `presence` — `{"device":"desktop","online":true|false,"lastSeenAt":"<iso>"}`, sent to every connected mobile device for the account whenever the desktop connects or disconnects (including on ungraceful drop, detected by a 30s ping/pong heartbeat).

### Mobile → desktop (request types; desktop always replies with a `response` echoing the same `id`)

| `type` | `payload` in | `payload` in the `response` |
| --- | --- | --- |
| `list_dashboard` | `{}` | `{ok:true, data: Dashboard}` (see `packages/types` `Dashboard`, trimmed — no `agent.currentActivity`/`stats.claudeCostUsd`, see below) |
| `list_applications` | `{}` | `{ok:true, data: ApplicationListItem[]}` |
| `get_application` | `{id}` | `{ok:true, data: ApplicationDetail}` |
| `approve_application` | `{id}` | `{ok:true, data: Application}` |
| `reject_application` | `{id, reason?}` | `{ok:true, data: Application}` |
| `apply_application` | `{id}` | `{ok:true, data: {runId}}` (fire-and-forget like the desktop's own apply button; follow with `changed` pushes) |
| `answer_application_questions` | `{id, answers: [{question, answer}]}` | `{ok:true, data: Application}` |
| `mark_manual_application_complete` | `{id, note?}` | `{ok:true, data: Application}` |
| `set_application_status` | `{id, status: "INTERVIEW"\|"OFFER"\|"WITHDRAWN"\|"REJECTED", note?}` | `{ok:true, data: Application}` |
| `request_file` | `{path, kind:"pdf"}` | `{ok:true, data: {name, base64}}` (desktop refuses anything over 4 MB or outside its data directory with `ok:false`) |

Every error reply is `{"ok":false,"error":{"code":"...","message":"..."}}`
using the same `UserFacingError` shape and codes the Tauri commands already
return (`INVALID_TRANSITION`, `AGENT_BUSY`, `NOT_FOUND`, `VALIDATION`, …),
so the phone can show the same message the desktop would.

### Desktop → mobile (push, no reply expected)

- `changed` — `{"collections": ["applications","jobs"]}` — mirrors the
  desktop UI's own `data:changed` Tauri event; the phone reacts by
  re-issuing the relevant `list_*`/`get_application` request, exactly like
  `apps/desktop/src/lib/events.ts` does today.
- `agent_status` — a trimmed `AgentStatus`: `{"state","paused","runKind"}`
  only. Never the free-text `currentActivity`, never `CLAUDE_ACTIVITY`
  events, and never per-step `AgentEvent`s — those can contain fragments of
  resume or job text and are desktop-only. The phone is a review surface,
  not a second Agent Activity console.

## Trimmed shapes sent to mobile

`Dashboard.agent` sent to mobile omits `currentActivity`;
`Dashboard.total`/`today` (`DashboardCounts`) and `ApplicationListItem` /
`ApplicationDetail` are sent exactly as `packages/types` defines them
otherwise. `Job.description` is included (the phone needs it to review),
but the desktop caps every string field it sends at 20,000 characters as a
defensive limit.

## Security notes

- The relay must run behind TLS in production (`wss://`); both the desktop
  and mobile clients refuse to send a password over a relay URL that
  doesn't start with `https://` unless the user opts into a clearly labeled
  "insecure / local testing" toggle.
- The relay logs the envelope `type`, the account id and the device id at
  debug level, never the `payload`.
- A device token compromise only grants relay access for that one account's
  message routing and file requests already permitted to that device kind —
  it cannot reach MongoDB Atlas, Claude, or the local filesystem beyond what
  the desktop's own handler exposes (job/application data and small PDFs
  under the data directory).
